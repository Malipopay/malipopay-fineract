# Local proof of the core banking stack, 2026-09-09

## What was proven, and what was not

Run on a macOS developer machine with Docker Desktop, against the compose stack in
`deploy/compose/`. Full console output is in `proof-2026-09-09.txt` beside this file.

**Proven.** The compose stack starts from cold on an empty volume, Liquibase migrates both
databases, and a Fineract tenant named `uat` in `Africa/Dar_es_Salaam` comes up healthy. A
savings product, a customer, a savings account, a deposit, a replayed deposit, a withdrawal
and a statement all behave correctly through the REST API. Authentication, tenant isolation
and the closed actuator surface were each checked against a deliberate control that would
have failed had the check been vacuous.

**Not proven.** This ran on `apache/fineract:latest`, which is the upstream `develop` branch
HEAD, not release 1.15.0. Apache publishes no Docker image for 1.13.0 and later, so the
release image has to be built from source by
`.github/workflows/malipopay-docker-build.yml`, and that build needs a JDK, which this
machine does not have. What this run proves is the shape of the deployment and the
behaviour of the API. It does not prove the 1.15.0 image itself. Build the image, deploy it
to the UAT droplet, and run `proof.sh uat` against it before treating the stack as verified.

Also not covered here: NGINX and TLS, the IP allow list, backup and restore, the
close-of-business job, and the operations console. Each has a runbook and each needs the
droplet.

## Four things this run taught, all of which changed the pack

**1. PostgreSQL 18 moved its data directory, and refuses to start if you mount the old one.**
The image now keeps data in a major-version subdirectory under `/var/lib/postgresql` so that
`pg_upgrade --link` works across one mount point. A volume at the conventional
`/var/lib/postgresql/data` is detected as an unused mount and the container exits rather
than risk writing two copies. The compose file mounts the parent directory and says why.

**2. `paymentTypeId` is mandatory on savings deposits and withdrawals.** Neither posts
without it. Fineract seeds three payment types; the pack creates a fourth named
"Malipopay rail" so the money trail names the rail the funds actually moved on. The banking
middleware must map each Malipopay rail to a Fineract payment type at configuration time.

**3. The idempotency cache stores failures too.** A first attempt that failed validation with
HTTP 400 was replayed on the second call as the same 400, with `x-served-from-cache: true`.
The key is bound to the outcome, not to the intent. So a corrected retry must carry a NEW
key, and the middleware must mint one key per instruction rather than one per attempt, with
a fresh key whenever the request body changes. Getting this backwards produces a funding
instruction that can never succeed.

**4. `shortName` on a savings product is capped at four characters.** Trivial, but it fails
the whole create with a validation error, and product codes have to be designed around it.

## Reproducing this

```bash
cd deploy/env && cp fineract.env.example .env.local   # then set the local ports and passwords
cd ../.. && docker compose \
  -f deploy/compose/docker-compose.yml \
  -f deploy/compose/docker-compose.local.yml \
  --env-file deploy/env/.env.local up -d
CBS_LOCAL_ENV=deploy/env/.env.local ./deploy/scripts/proof.sh local
```

Tear down with `down -v`. The `-v` matters: without it the next run starts on a migrated
database and proves less than you think.
